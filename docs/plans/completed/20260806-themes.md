# Themes: five built-ins and cross-session persistence

## Overview

Replace the two-state light/dark toggle with a theme picker offering five VS Code-inspired
built-in themes plus a "System" option that follows the OS. The chosen theme is persisted
server-side in `~/.revgate/config.json`, so it survives across sessions and invocations.

Built-in set: Dark Modern, Light Modern, Monokai, Solarized Light, Dracula — plus a `system`
option, the default, resolving to Dark Modern / Light Modern via `prefers-color-scheme`.

**Why server-side persistence is required, not optional:** the review server listens on a
random port (`server.listen(0, …)` in `src/server.ts`), so every run is a distinct browser
origin with its own empty `localStorage`. The existing `localStorage` theme memory therefore
never survives a session today — it has never once worked for anyone. `~/.revgate/config.json`
is the only place a choice can actually persist.

User-authored themes are deliberately out of scope; see "Deferred" at the end for the reasoning.

## Design

**Config file** `~/.revgate/config.json`:

```json
{ "theme": "dracula" }
```

`$REVGATE_CONFIG_DIR` overrides the *directory* the file lives in — the file is always
`config.json` inside it. This is deliberately not the same shape as `$REVGATE_HISTORY_DIR`,
which names the history directory itself (`~/.revgate/history`); the README must say which is
which, because setting `$REVGATE_CONFIG_DIR` to a `history`-shaped path is the obvious mistake.

**Theme model.** A theme is `{ id, name, type: "dark" | "light", colors }`, where `colors` is a
*complete* map over every custom property the page themes. Nothing merges over a base palette:
each built-in stands alone, so reading one file tells you exactly what a theme looks like.

`type` is not decoration. It drives `document.documentElement.style.colorScheme`, which is what
makes the browser render the picker's own dropdown, the scrollbars and any native control in
the matching mode — without it a dark theme gets a light dropdown floating over it.

**The `system` id is a first-class value**, not just a fallback: it is a member of the id set
`GET /api/themes` returns and `POST /api/theme` accepts, and it is what a fresh install
resolves to. It carries no palette of its own — the client resolves it to Dark Modern or Light
Modern through `matchMedia("(prefers-color-scheme: light)")` and re-resolves on that query's
`change` event, so a mid-review OS switch follows.

**No colour validation, deliberately.** Every palette is a TypeScript literal compiled into the
build, so there is no untrusted colour value anywhere in this feature — the only user-supplied
value is the theme *id* in `config.json`, which is validated by set membership. If user-authored
themes ever land, a value allow-list has to come back with them: a custom `--bg: url(https://…)`
would fire an outbound request from a page that is otherwise deliberately network-free (see the
self-hosted font comment at the top of `public/index.html`), and the server sets only
`frame-ancestors`, so nothing else would stop it.

**Failure posture.** Nothing in `src/theme.ts` throws: an unreadable config, malformed JSON, or
a read-only home directory warns to stderr and degrades to `system`. A review gate must never be
wedged by a cosmetic subsystem. The same rule extends to the client — see Task 3.

**Config writes are atomic** (write a temp file next to the target, then `rename`). A crash
mid-write would otherwise leave a truncated `config.json`; because the read path degrades
silently by design, the user would not see an error, they would just quietly lose their theme.

**One-field config, written down as an assumption.** `writeThemeConfig` rewrites the whole file.
That is safe only while `theme` is the sole key — the moment a second field lands, a
read-modify-write from a stale snapshot starts clobbering it, and two review servers can easily
be running at once. Whoever adds the second field owns fixing this.

**First-paint flash.** The page fetches themes after load, so a non-default-theme user may see
one frame of the built-in dark palette. Accepted rather than worked around: the `localStorage`
pre-paint hint that exists today cannot help (new origin every run), and injecting the palette
into the served HTML would mean templating a currently-static file. The `prefers-color-scheme`
CSS block is kept so system-light users — the default — see light immediately.

## Deferred: user-authored themes

Dropping a JSON theme into `~/.revgate/themes/` was cut from this plan, and the reasoning is
worth recording so it is a decision rather than an omission.

The sibling project revdiff (`../revdiff`) ships this and it is roughly 2,200 lines including
tests. Almost none of that is the file format — it is the ergonomics that make the format
usable: `--dump-theme` to generate a valid starting file, `--install-theme` to validate before
adopting, `--list-themes`, an embedded gallery of ten example themes, and auto-installing them
on first run so there are real files on disk to copy. Shipping the loader without any of that
gives a user a format to hand-author against one README example, where a validation failure
surfaces only as a stderr warning nobody reads — revgate's output is a browser page.

It also drags in the colour-value allow-list described under Design, which is the only real
security surface in the whole feature.

If it is ever picked up, the bootstrap path is the requirement, not the loader.
